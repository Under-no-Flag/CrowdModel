# 宏观人群模型仿真性能优化方案

日期：2026-06-16
范围：`D:\CrowdModels\codes\crowd_bellman` 求解内核与单次仿真，结合 `results\g6_horizontal_comparison` 实验的规模与耗时。
目标：大幅降低每次仿真耗时，从而缩短整组优化实验的墙钟时间。

---

## 0. 结论先行（TL;DR）

单次仿真的耗时几乎全部来自 **HJB/Bellman 求解器 `solve_bellman`**（纯 Python `heapq` 的类 Dijkstra 标签法），在 128×96 网格、3 个分组场景下，单次求解约 **82 ms**，占每个 Bellman 步耗时的 **99%~100%**；密度更新、方向恢复、速度计算等加起来不足 1%。

因此优化优先级非常明确：

| 层次 | 手段 | 预期单次仿真加速 | 改动风险/成本 |
|---|---|---|---|
| L0 立即见效 | 提高 worker 数（6→16）、按需重算 Bellman、清空时早停 | 实验整体 2.5~4× | 极低 |
| L1 内核加速 | Numba/Cython 重写 `solve_bellman`，或改用 Fast Iterative Method | 单次 8~30× | 中 |
| L2 循环结构 | 多组并行（进程/nogil）、限制活跃求解区域、warm start | 额外 2~3× | 中 |
| L3 搜索层 | 强化多保真筛选、评估缓存、代理模型减少昂贵评估次数 | 实验整体再 2~5× | 中高 |

L0 在 1 天内即可落地，可把 G6 这类实验从约 8 小时压到 2~3 小时；叠加 L1 的内核重写后，单次高保真仿真可从约 80 s 降到 3~10 s 量级。

## 1. 测量方法与环境

- 机器：CPU 20 逻辑核（`os.cpu_count() == 20`）。
- 场景：`scenes/examples/g2_multistage_directional/run_baseline.toml`，即 G6 的基线场景。
  - 网格 `nx=128, ny=96`，共 12288 单元，其中可行走 10006；`dx=0.5`；分组数 **3**。
- 测量：用生产后端（`bellman_backend="optimized"`、`direction_recovery_backend="vectorized"`）对各内核函数单独计时取均值。

各内核单次调用耗时（单分组）：

| 函数 | 单次耗时 | 说明 |
|---|---|---|
| `solve_bellman`（optimized） | **81.9 ms** | 纯 Python heapq 类 Dijkstra，主导项 |
| `recover_optimal_direction`（vectorized） | 1.25 ms | 已向量化，廉价 |
| `update_density` | 0.18 ms | 显式迎风对流，廉价 |
| `greenshields_speed` | 0.018 ms | 可忽略 |
| `compute_total_density` | 0.010 ms | 可忽略 |

每步耗时（3 组）：

- 含 Bellman 的步：`3×(82+1.25) + 其它 ≈ 250 ms`（求解+方向恢复占约 99.5%）。
- 仅对流的步（被 `bellman_every` 跳过 Bellman 时）：约 **0.56 ms**。

由此可见两点：
1. **Bellman 求解是唯一值得优化的热点**；密度演化已足够快。
2. **`bellman_every` 是最直接的乘法因子**：跳过一次 Bellman 即省下约 250 ms，做一次对流仅 0.56 ms。

## 2. 单次仿真的耗时模型

记每步含 Bellman 的耗时 `T_B≈250 ms`、仅对流耗时 `T_A≈0.56 ms`、总步数 `N`、Bellman 周期 `k=bellman_every`，则

```
单次仿真耗时 ≈ (N/k)·T_B + (N·(1-1/k))·T_A ≈ (N/k)·T_B
```

代入各配置（3 组）：

| 配置 | 步数 N | bellman_every | 估算单次耗时 | Bellman 占比 |
|---|---|---|---|---|
| screen（g6.toml） | 60 | 6 | ~2.5 s | ~99% |
| optimization / high_fidelity（g6.toml） | 1600 | 5 | **~80 s** | ~99% |
| baseline（run_baseline.toml） | 4000 | 1 | **~1000 s** | ~100% |

关键观察：基线配置 `bellman_every=1` 且 `steps=4000`，意味着每步都对 3 组各做一次 82 ms 的全网格 Dijkstra，单次仿真接近 17 分钟，是开销失控的根源；G6 通过 `bellman_every=5` 已显著缓解。

## 3. G6 实验级消耗剖析

`results\g6_horizontal_comparison` 是一个混合保真度的超参数/控制优化实验（6 种方法 × 5 个种子），每次候选评估即一次完整仿真：

- 实际产出 **10,309 个 `summary.json`**（即约 1 万次仿真），收敛曲线约 1 万行评估记录。
- 三档保真度：screen（60 步，便宜）、optimization 与 high_fidelity（各 1600 步，约 80 s/次）。
- 并行：`workers=6`（仅用满 20 核中的 6 核）。

墙钟估算（按目录时间戳，主体运行 5/24 06:36→14:31，约 **8 小时**）：

- 平均每次仿真 ≈ `8h × 6 workers / 10309 ≈ 16.7 s`，与「约 8 成 screen（~2.5 s）+ 约 2 成高保真（~80 s）」的混合相符。
- 即昂贵的高保真评估贡献了绝大部分计算量，但被 screen 在数量上稀释。

实验级三大可优化点：
1. **并行度未用满**：6/20 核，直接提高即近线性收益。
2. **昂贵评估占主导**：每个 80 s 的高保真仿真完全受 Bellman 内核支配，内核加速对这部分是乘法收益。
3. **重复与冗余评估**：已有 `G5EvaluationCache`（按归一化控制向量缓存），但仿真本身无「人群清空即停」的早停，固定跑满 1600 步。

## 4. 分层优化建议与预期成效

### L0 — 立即见效（低风险，建议优先，1 天内）

**L0.1 提高并行 worker 数。**
G6 仅用 6/20 核。改 `g6.toml` 的 `workers` 到 14~16（留余量给系统与内存）。
预期：实验墙钟近线性下降，6→16 约 **2.6×**。代价：内存占用上升（每 worker 独立进程，注意 10k 网格数组不大，可行）。

**L0.2 人群清空早停。**
`runner.simulate_case` 主循环目前仅以 `step<steps and time<horizon` 为终止条件，固定跑满。绝大多数评估在人群疏散完毕后仍空转数百步。
建议：在每步统计总质量后，若 `剩余质量 < ε·初始质量`（如 1%）连续若干步，则提前结束。
预期：对易疏散的候选，1600 步常可在 600~1000 步内结束，**节省 30%~60% 步数**；对优化搜索中大量「较优、疏散快」的候选尤其有效。风险：需保证目标函数（J1 总疏散时间等）在早停后仍正确累计，需要核对 `metrics.build_summary` 的口径。

**L0.3 适度增大 `bellman_every`。**
速度场 `f(ρ)` 随密度缓慢变化，Bellman 值函数在相邻步间高度相关。把高保真 `bellman_every` 从 5 提到 8~10，单次耗时近似按比例下降。
预期：单次再降 **1.5~2×**。风险：过大会让方向场滞后于密度，影响精度，需以 G6 目标值对比做敏感性验证（5 vs 8 vs 10）。

> L0 合计：实验整体约 **2.5~4×**（例如 8h → 2~3h），且基本不动核心代码。

### L1 — Bellman 内核加速（核心，收益最大）

热点是 `_solve_bellman_optimized` 的 Python 层 `heapq` 循环：每次 pop 后遍历 8 方向、做 Python 级比较与 push，节点约 1 万、边约 8 万，纯解释执行。

**L1.1 Numba JIT（推荐首选）。**
将内核改写为 `@njit` 函数，用 typed 数组实现二叉堆或直接用 Numba 支持的结构；解除 GIL（`nogil=True`）后还能配合多组并行。此类标签法在 Numba 下通常 **10~50×**。
预期：单次 82 ms → **2~8 ms**；高保真仿真 80 s → **3~10 s**。成本：引入 numba 依赖、首次编译开销（可缓存 `cache=True`）。需新增内核后端 `bellman_backend="numba"` 并用现有 `tests/test_core_backends.py` 校验与 python/optimized 后端数值一致。

**L1.2 Cython / C 扩展（替代方案）。**
若不愿引入 numba，可用 Cython 写内核，性能相近，但构建链更重、跨平台分发更麻烦。

**L1.3 算法替换：Fast Iterative Method (FIM) / Fast Sweeping (FSM)。**
各向异性 eikonal 可用 FIM/FSM 求解，天然 SIMD/向量化、可 warm start、易并行（甚至 GPU）。比 Dijkstra 更适合「每步重解且解高度相似」的场景。
预期：与 Numba 同量级或更好，且 warm start 收益叠加（见 L2.3）。成本：需要重新实现并验证与现有离散 8 方向 HJB 的等价性（参考 `verify_unidirectional_hjb.py` 的口径）。

> L1 是把高保真仿真从「分钟级」拉到「秒级」的关键。建议先做 L1.1（投入产出比最高）。

### L2 — 仿真循环结构优化

**L2.1 多组并行求解。**
当前 3 组在每个 Bellman 步串行求解（`runner.py` 的 `for key, group in groups.items()`）。纯 Python 下受 GIL 限制（故现有 threaded benchmark 提升有限），但：
- 配合 L1.1 的 `nogil` Numba 内核，可用线程池真正并行，**约 3×**（组数）。
- 或在内核重写前，用进程池在评估级并行已由 L0.1 覆盖。
预期：与 L1 叠加约 **2~3×**。

**L2.2 限制活跃求解区域。**
密度为零的大片区域其最优方向不影响演化。可只在「占用单元的包围盒 + 安全边距」内求解 Bellman，随人群移动动态调整。
预期：疏散后期网格大量空置时，节点数大幅下降，**1.3~2×**（场景相关）。风险：边界处理需谨慎，避免方向场在活跃区边缘失真。

**L2.3 Warm start。**
Dijkstra 标签法不易热启动，但 FIM/FSM（L1.3）可用上一次 `phi` 作为初值，相邻步迭代次数骤降。
预期：与 FIM 配合时 **2×+**。

### L3 — 搜索/实验层优化

**L3.1 强化多保真与早筛。**
高保真评估是计算大头。可：提高 screen 阶段的淘汰率、减少进入 high_fidelity 的候选数（`high_fidelity_top_k=10` 可下调）、用 optimization 档替代部分 hf 复核。
预期：高保真次数减半即整体 **~1.5×**。

**L3.2 用满评估缓存并扩展。**
已有 `G5EvaluationCache` 按归一化控制向量缓存。建议核对各方法是否都走缓存、是否存在因数值微差导致的缓存未命中；可对控制向量做更稳健的量化键。
预期：去重收益与方法相关，通常 **10%~30%**。

**L3.3 代理模型 / 早停搜索。**
对 random_search / SA 等，可用便宜保真度构造代理筛选，减少昂贵评估调用次数（HCMBO 已部分采用 BO 思想，可推广到其它 baseline 的预筛）。

## 5. 推荐落地路线图

1. **第一步（当天）**：L0.1 提高 workers + L0.2 早停 + L0.3 调 `bellman_every`。实验级约 2.5~4×，零核心改动。
2. **第二步（数天）**：L1.1 Numba 重写 `solve_bellman`，新增 `numba` 后端并用 `test_core_backends` 校验数值一致。单次高保真 80 s → 3~10 s。
3. **第三步**：L2.1 多组 `nogil` 并行 + L2.2 活跃区域裁剪，再 2~3×。
4. **第四步（按需）**：L1.3 FIM + L2.3 warm start（若仍需更快/上 GPU），及 L3 搜索层精简。

整体预期：在不牺牲精度（以 G6 目标值做回归校验）的前提下，**单次高保真仿真从约 80 s 降到个位数秒级（约 10~25×）**，G6 这类约 8 小时的整组实验有望压缩到 **20~40 分钟**。

### 7.4 采用建议

采用 L1.1+L1.3 联合后端作为默认生产路径，即 `bellman_backend="sweeping"`。该后端把 Fast Sweeping / FSM 风格松弛放在 Numba JIT 下执行，内核级快于单独 L1.1 `numba`，并已通过与 `optimized` 的逐元素误差和端到端 summary 误差验证。`bellman_backend="numba"` 保留为 Dijkstra 标签法的 Numba 对照后端，便于后续复杂障碍或强各向异性场景回归对比。

### 7.5 L1.1 与 L1.3 能否同时引入

可以同时引入。推荐方式不是把两个后端串联调用，而是让 L1.3 的 Fast Sweeping / FSM 风格算法本身用 L1.1 的 Numba JIT 编译执行。因此组合后端定义为：

```python
bellman_backend = "sweeping"  # alias: "fsm"
```

其含义是：仍求解与现有 Dijkstra 标签法相同的 8 方向离散 Bellman 方程，但求解迭代方式换成 Fast Sweeping 风格 Gauss-Seidel 松弛，并用 `@njit(cache=True, nogil=True)` 编译。这样组合不会改变动力学模型；是否可采用取决于与 `optimized` 后端的逐元素误差和端到端 summary 误差。

组合验证命令：

```bash
cd codes
python experiment_l1_combined_backends.py --config scenes/examples/g2_multistage_directional/run_baseline.toml --repeats 3 --steps 40 --save-every 99999 --output results/l1_numba_sweeping_combined_merge.json
```

实验结果：

| 方案 | 后端 | 组成 | 串行内核均值 | 内核加速 | 40 步仿真 | 仿真加速 | `phi` 最大误差 | summary 最大误差 |
|---|---|---|---:|---:|---:|---:|---:|---:|
| 基线 | `optimized` | Python heapq Dijkstra | 143.29 ms | 1.00× | 5.75 s | 1.00× | 0 | 0 |
| L1.1 | `numba` | Numba + 二叉堆 Dijkstra | 7.09 ms | 20.20× | 1.17 s | 4.93× | 0 | 0 |
| L1.1+L1.3 | `sweeping` / `fsm` | Numba + Fast Sweeping/FSM 风格松弛 | 6.12 ms | 23.41× | 1.26 s | 4.57× | 4.26e-14 | 2.08e-17 |

结论：

- **可同时引入**，并且组合后端在内核级优于单独 L1.1：`7.09 ms → 6.12 ms`。
- **精度没有实质下降**：`phi` 误差为 `4.26e-14`，summary 最大误差为 `2.08e-17`，均为浮点舍入量级。
- **端到端短仿真收益与 L1.1 同量级**：40 步场景下 Bellman 已被压到很小，方向恢复、密度更新、统计和 I/O 占比上升，所以 `numba` 与 `sweeping` 的 40 步仿真时间分别约 `1.17 s` 与 `1.26 s`。
- **采用策略**：默认生产路径切到 `sweeping/fsm`；`numba` 保留为同一离散方程的 Dijkstra 标签法对照后端，后续继续用更多障碍/强各向异性场景验证收敛轮数和误差。
